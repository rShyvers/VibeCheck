# Vibecheck

A consumer product with formally verified properties, built for the Vibecheck hackathon. See [RULES.md](RULES.md) for what we're judged on and [CLAUDE.md](CLAUDE.md) for how the verification work is done.

## Quick start

The project ships a portable **Temurin JRE 21** in `vendor/jre/`, so you don't need Java installed.

### macOS / Linux
```sh
git clone --recurse-submodules https://github.com/rShyvers/VibeCheck && cd VibeCheck
make install && make run
```

`--recurse-submodules` fetches the pinned Semantic MIPS (see below). A plain
`git clone` also works: `make install` fetches the submodule automatically.

### Windows
```bat
install.bat
run.bat
```

`install` extracts the JRE for your platform into `.jre/` (gitignored) and prints its version. `run` launches the project with that JRE. `make clean` removes the extracted JRE.

The bundled runtime is a **JRE** (no compiler), so compiled output in `out/` is committed and `make run` works as-is. After changing sources, recompile with any system JDK via `make compile` (Windows: `javac -d out src\*.java`) and commit the result.

## What you're looking at

`make run` opens the **verdict view** (a local web page, no install), with three tabs:

- **Run code** — paste MIPS assembly and hit Run. The server pipes it to `MipsRun`, the real interpreter built from the Lean semantics, and the page shows what the verified machine does: program output, halt reason, step count, and all 32 registers. **On Linux x86_64, this works immediately after `make install`** — see "The MipsRun interpreter" below. On other platforms, the tab says so until you build one yourself with `make build-semantics` (needs [elan](https://github.com/leanprover/elan)).
- **Tic-Tac-Toe** — a playable game whose entire rules engine (move validation, win/draw detection, the opponent's strategy) is a MIPS program run through the same `/run` endpoint as Run code, unchanged — the browser holds only the board. A "show the MIPS program for this move" panel reveals exactly what ran. See PLAN.md for how it was built and tested (34,529 board/move combinations, zero failures).
- **Verdict** — the formal-verification verdict of the MIPS work: proof gates, differential agreement against MARS 4.5, and equivalence claims with counterexamples, so bug-freeness is visible at a glance. The tab loads `/verdict.json`; until a real Lean harness run writes `out/verdict.json`, it shows the bundled sample verdict (the true v1 equivalence-corpus result: 5 real equivalences plus 2 deliberately buggy variants, caught).

## What's trusted

- **Bundled runtime:** Eclipse Temurin OpenJDK 21 (JRE), one archive per platform in `vendor/jre/`. This is the only external dependency; nothing is downloaded at install time.
- **Pinned semantics:** the Lean work lives in its own repo and is embedded here as a git submodule at a pinned commit, so every run of this project uses exactly the semantics version the pin names (see "Semantic MIPS (submodule)").
- Verification claims and their trusted surface are documented here as they land.

## Semantic MIPS (submodule)

The Lean semantics live in [rShyvers/semantic-mips](https://github.com/rShyvers/semantic-mips) and are embedded here as a **git submodule** at `semantic-mips/`, pinned to a specific commit. A plain `git clone` leaves that folder empty; `make install` (or `git submodule update --init`) fetches the pinned version, so `make install && make run` works from a fresh clone.

Current pin: `9cf0297` (their `main`) — re-pinned from the original `abf580d` once the blocker below was fixed. `main` gained a lot since the original pin: real branch delay slots, `jr`/`jalr` (with kernel-checked spec theorems, not just implementations), variable shifts, 226+ proven theorems (up from ~12 with real coverage), and more.

**The re-pin blocker, and how it was fixed.** `main`'s branch delay slots (the instruction right after any `beq`/`bne`/`blez`/`bgtz`/`j`/`jal` always executes, matching real MIPS32 hardware) broke the Tic-Tac-Toe engine, which was written assuming no delay slot. Checked directly before fixing anything: running the old engine against `main` produced **18,356 failures** out of ~70,000 checks. The fix: both Tic-Tac-Toe templates (Hard and Easy) are generated by a Python script (`gen.py`, kept outside this repo during development), which now inserts a `nop` after every one of the 72 (Hard) / 52 (Easy) branch/jump instructions it emits — the standard, textbook-correct way to write delay-slot-safe MIPS, restoring exactly the original behavior. Re-verified with the same rigor the engine originally earned: 34,529 board/move combinations + all `3^9` boards + the full game-tree replay, for **both** opponents, zero failures, identical win/loss/draw counts to the original build; mutation-tested (9 broken variants, all still caught with the same failure counts). The other three shipped programs (hello world, both bug examples) have no branches and were unaffected by any of this.

**Known limitation, carried from their side:** `MipsRun` wraps `Asm.assemble`/`initialState`/`Step.run` only, so `.data` segments are never copied into memory — a program that loads a string with `la`+`syscall 4` will read all-zero memory instead. The bundled sample program was written to avoid this (it prints via register values only); keep that in mind for any future sample/demo program.

The demo always runs against the **pinned** commit, never a moving branch. To build against a newer semantics: `cd semantic-mips && git fetch`, check out the commit you want, then from the repo root commit the updated pin (`git add semantic-mips`).

## The MipsRun interpreter

`MipsRun` (the executable behind the Run code and Tic-Tac-Toe tabs) is vendored pre-built for **linux-x64** at `vendor/mipsrun/linux-x64/MipsRun`, built from the pinned commit above, same idea as the bundled JRE: a stripped, statically-linked-for-Lean binary that needs only glibc at runtime, confirmed to run correctly with no Lean toolchain present at all (checked in a fully scrubbed environment — no `elan`/`lake`/`lean` reachable, not even on `PATH`). `make install` copies it into `.mipsrun/MipsRun` automatically, so on Linux x86_64, `make install && make run` gives you a fully working Run code tab and a playable Tic-Tac-Toe immediately, straight from a fresh clone — no Lean toolchain required.

On other platforms (no vendored binary yet), `make install` says so plainly and the tabs show an honest "interpreter not built" state until you run `make build-semantics` (needs elan/lake; fetches the Mathlib cache, then builds).

To refresh the vendored binary after re-pinning: `cd semantic-mips && lake exe cache get && lake build MipsRun`, then copy `.lake/build/bin/MipsRun` to `vendor/mipsrun/linux-x64/MipsRun` (stripping it first with `strip` is optional but keeps the repo smaller — the committed copy is ~3 MB stripped vs ~5 MB unstripped).

## Verification gates

**Semantic MIPS now lives in its own repo:**
[rShyvers/semantic-mips](https://github.com/rShyvers/semantic-mips). It was
extracted out of this project (full build history preserved) so the Lean
semantics — and only the Lean semantics — can be read, built, and reviewed
without anything else in this project in the way. That repo's own README has
the full trust chain, both verification gates, their current status, and the
3 documented `sorry`s with closed substitutes. Summary below; see the other
repo for the complete, current picture.

The Lean project (Lean 4.35.0) implements and proves properties
of **Semantic MIPS** — a small-step semantics of the v1 MIPS dialect,
written in Lean, plus the kernel-checked theorems that say it matches its
spec. See `CLAUDE.md` for the full approach to writing and checking these
proofs.

The trust chain is plain: the MIPS language spec lives in `docs/spec/`
(`INSTRUCTION-REF.md` and `SPEC-NOTES.md`), human-written and sourced to
the real MARS 4.5 simulator's behavior. Semantic MIPS
(`Semantics/Step.lean`'s `step` function) is the Lean implementation
of that spec. The spec's key claims are kernel-checked theorems
(`Semantics/Specs/StepSpec.lean`), judged by `lake comparator`
against a trusted statement file (`comparator.json`), and the whole
semantics is differentially validated against real MARS 4.5 on a
12-program corpus (`DiffHarness`). The project's narrative is deliberately
simple: formally verify the MIPS spec into Semantic MIPS, validate it
against MARS, then use it to find a real arithmetic bug in a sealed
program.

Two gates decide whether a proof counts as "done":

- **`lake check`** rebuilds the project's default target, replays the
  result through Lean's own kernel, and fails if anything uses an axiom
  beyond the handful the kernel itself treats as standard. It is
  all-or-nothing over its whole target: one unfinished proof anywhere in
  it fails the whole gate.
- **`lake comparator`** checks a named list of theorems against a config
  file (`comparator.json`) stating which axioms are allowed. Unlike
  `lake check`, it works theorem-by-theorem, so it is the right tool for a
  file that mixes finished and unfinished proofs.

**Permitted axioms (both gates):** `propext`, `Classical.choice`,
`Quot.sound` — the three axioms built into Lean/Mathlib's logic that
`#print axioms` treats as a clean proof (CLAUDE.md §7). Anything else
(most importantly `sorryAx`, which every unfinished `sorry` adds) fails
both gates.

### Current status

- **`lake comparator`: green.** Config: `comparator.json`. Trusted
  surface (8 of the spec's 21 theorems — picked to cover one theorem from
  each kind of claim the spec makes, not the whole file):
  - `add_spec_raw`, `sub_spec_raw` — arithmetic plus signed-overflow
    trapping (`add`, `sub`).
  - `div_by_zero_spec` — a division edge case leaves `hi`/`lo` untouched.
  - `beq_taken_spec` — branch semantics.
  - `jal_sets_ra` — jump-and-link semantics.
  - `lw_spec_raw` — memory load semantics.
  - `add_overflow_not_wrapped` — a bad-output rejection: overflow halts,
    it never silently wraps.
  - `zero_write_not_observable` — the `$zero`-register invariant, closed
    form.

  The `challenge_module` and `solution_module` in `comparator.json` are
  both `Semantics.Specs.StepSpec`: there is one statement of each theorem,
  not a second copy in a separate `Challenge` file. A second copy would
  only add a place for the trusted statement and the proved statement to
  quietly drift apart; comparator's theorem-by-theorem kernel check and
  axiom audit give the same guarantee without that risk. Verified by
  running `lake comparator` to exit code 0 (see the project's closeout
  notes for the full transcript).

- **`lake check`: green, with one documented, scoped exclusion.**
  `lake check` has no per-theorem axiom allowlist — it is pass/fail over
  its whole default target — so a file with any `sorry` in it fails the
  gate outright. `Semantics/Specs/StepSpec.lean` (the spec file) has 3 such
  `sorry`s (below), so it is excluded from `lake check`'s default target:
  the default target is a new `Checked` library (`Checked.lean`,
  set as the default in `lakefile.toml`) covering everything *except* the
  spec file — `Word`, `Types`, `State`, `Instruction`, `Asm`, `Step`, and
  their own unit tests. `lake check` kernel-replays exactly that and
  passes using only the three permitted axioms. The full project
  (including the spec file) is still built by `lake build Semantics`, and
  the spec file's finished theorems are still checked by `lake
  comparator`, above. Nothing is silently dropped; see `Checked.lean`'s
  header comment for the same explanation in-repo.

### Open items: 3 documented `sorry`s

All three are in `Semantic MIPS`'s `Semantics/Specs/StepSpec.lean` (see that
repo), each with a closed, weaker version proved instead and a concrete
`#guard`-checked example. Full detail in [that repo's
README](https://github.com/rShyvers/semantic-mips#open-items-3-documented-sorrys).
